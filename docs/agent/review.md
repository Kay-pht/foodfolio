# AIレビューと停止条件

## 責務分離

初回の実装と必要なローカル検証・CIの完了後、Implementerは人間からの追加指示を待たず、新規の別チャットを作成して独立Reviewerへレビューを依頼する。同じ会話内のサブエージェント、実装会話のfork、Implementer自身による最終レビューで代用しない。初回だけ実装履歴を引き継がないReviewerチャットを作成し、その後はImplementer / FixerとReviewerの2つのチャットを維持して往復する。元のImplementerが元チャットでFixerを担当してよい。

- Implementer: 仕様に基づく実装、テスト追加、検証、コミット、独立レビューの依頼と結果確認を行う。自分の実装に最終LGTMを出さない。
- Reviewer: 初回はfresh contextで、再レビューは同じチャットに保持したレビュー履歴と最新情報を使って仕様、PR差分、関連コード、検証結果を確認し、レビュー対象のコードを変更しない。結果は `LGTM` または `AUTOMATION_BLOCKED` とし、根拠・指摘の分類・確認事項を添える。LGTM記録後の外部Task-Listのタスク内容更新・コミットは、下記の同期手順に限り認める。
- Fixer: 元の実装チャットで、既存仕様に対する具体的なバグ・不具合を修正し、必要な検証を再実行する。仕様変更の提案はユーザー確認前に実装しない。修正後は初回に作成した同じReviewerチャットへ再レビューを依頼する。

既に承認された [アラート修正ハーネス](alert-repair.md) の案件は、制御プログラムが工程ごとに独立セッションを起動してIDを保存・検証する既存プロトコルを維持する。ハーネス自体の変更は通常の別チャットレビューを行う。このルールの追加だけでハーネスのコードや権限を変更しない。

AIエージェントは最終マージを実行しない。マージは人間だけが行う。

## 別チャットへの依頼と元チャットへの返却

1. Implementerは初回だけ新規チャット作成ツールで同じプロジェクトの独立Reviewerチャットを作成する。再レビューでは同じReviewerチャットにメッセージ送信ツールで更新SHA・修正内容・最新の検証情報を渡し、その結果を待つ。元の実装チャットの識別子、PR URL、レビュー対象HEAD SHA、元のユーザー要求、approved spec、成功済みコマンド一覧（配下の検証を含む）・対象SHA・終了コード・検証ログの参照先を渡す。実装会話全体は引き継がせず、Reviewerが正本を独立に読むための情報に絞る。ローカルのパス、チャットID、引き継ぎ用の記録をGit管理対象へ固定値として書き込まない。
2. Reviewerは最新HEADと指定SHAを照合し、共有checkoutのbranch切替・reset・ソース変更を行わずレビューする。途中でHEADが変われば古いSHAへLGTMを出さない。Reviewerは実装をしないため、さらにレビュー用チャットを再帰的に作成しない。
3. Reviewerは結果をレビュー用チャットに残し、ユーザーが明示的に許可した元チャットへの返却としてメッセージ送信ツールで通知する。送信権限の確認に必要なら元チャットのユーザー指示を読む。元チャットへの返却以外の第三者宛て送信へ許可を拡張しない。通知内容には対象SHA、指摘の根拠、再現条件、影響、既存仕様違反か仕様変更提案かの分類を含める。
4. Implementerは待機・状態確認ツールでレビュー結果を確認する。修正が必要な場合は元チャットでユーザーへその旨と根拠を報告してから、下記の分類に従って対応する。チャット作成・結果確認・返却ができない場合は、できたと報告せず不足する手段を明示する。
5. バグ修正後は必要な検証とCIを完了させ、更新したHEADを同じReviewerチャットに渡す。以前のLGTMや古いSHAの指摘解消だけでレビュー完了にしない。

## 通常レビューの機械的な記録

`npm run review:flow` はPRごとの台帳をGit管理対象外のGitディレクトリ配下 `foodfolio/review-flow-<PR番号>.json` に保存する。`CODEX_THREAD_ID` は実行中のチャットが提供する値を使い、別人の値へ上書きしない。未設定ならIDを創作せず停止し、環境の不足を報告する。共有checkoutでbranch切替やresetを行わない。

1. Implementerは必須ローカル検証・最新HEADのCI成功後、ReadyのPRで `npm run review:flow -- start` を一度実行する。同じPRの台帳を削除・初期化して履歴や上限をリセットしない。
2. ローカルの引き継ぎJSONをGit管理対象外へ保存する。`request` に元のユーザー要求の本文または参照、`specs` にapproved specのパス配列、`verification` に検証結果・ログ・CIの参照を記録し、`successfulCommands` を空でない配列として必須で渡す。各要素は `command`（実際に成功したコマンド）、`sha`（対象の完全なHEAD SHA）、`exitCode: 0`、`evidence`（成功結果のログ・CI参照）を持つ。`npm run verify` など包括コマンドで成功した配下の検証も、実際のログに基づき個別に列挙し、Reviewerが同じ検証を別名で繰り返さないようにする。修正後は新しいHEADでImplementerが検証し、その結果へ更新する。
3. 初回だけ新規チャット作成ツールで同じプロジェクトにReviewerチャットを作成する。再レビューは台帳の既存Reviewerチャットを使い、新規チャットを作らない。forkやサブエージェントを使わず、元チャットID、PR URL、完全なHEAD SHA、要求・spec・検証情報、この手順を渡す。Reviewerには台帳登録が完了するまで結果を記録しないよう伝える。
4. 初回は作成ツールで得た実際のチャットID、再レビューは同じ登録済みIDを使い、Implementerが `npm run review:flow -- request --reviewer <チャットID> --context <引き継ぎJSON>` を実行する。既存のLGTM証跡はここで無効化される。再レビューでは登録後、同じReviewerチャットへ最新HEAD・差分・成功コマンドの情報を送信し、状態確認・待機ツールで返却を待つ。チャット作成・再送信が失敗した場合は成功扱いにせず、架空のIDや別Reviewerへ切り替えて回避しない。
5. Reviewerは `npm run review:flow -- status` で自分のID・対象SHA・元チャットID・引き継ぎ情報を確認し、独立レビューを実施する。対象SHAに一致する成功済みコマンドは再実行せず、引き継がれた成功結果を信頼してコード・テスト内容・ログを読む。結果JSONの `reviewedSha` に完全な対象SHA、`verdict` に `LGTM` または `AUTOMATION_BLOCKED`、`findings` に指摘配列を記録する。各指摘は `classification`（`bug` / `specification_change` / `unclear`）、`evidence`（期待仕様とコード・ログ等の根拠）、`impact`（影響）、`reproduction`（再現手順または契約比較）を必須とする。指摘なしは空配列とする。追加検証を実行した場合は `additionalChecks` 配列へ `command`、`reason`（未検証の具体的な論点）、`evidence`、`exitCode` を記録する。追加検証なしは省略または空配列とする。
6. Reviewer本人が `npm run review:flow -- result --file <結果JSON>` を実行する。`bug` と `unclear` はblockerで、仕様改善提案だけではblockしない。結果は上書きできず、HEADが変わった結果は受理しない。
7. Reviewerは元チャットへの送信ツールで結果・分類・対象SHAを返す。成功した返却を確認してから `npm run review:flow -- delivered --reference <返却先と送信結果を確認できる参照>` を実行する。送信失敗・結果未確定なら返却済みと記録しない。
8. LGTMならReviewer本人が `npm run review:lgtm` を実行し、既存の外部Task-List同期と最終報告を行う。元チャットは状態確認・待機ツールで最終結果と証跡の保存を確認する。blockerなら元チャットが報告・修正・検証を行い、新しいHEADで手順2以降を繰り返す。

初回レビューとは別に、**修正→同じReviewerチャットでの再レビューは最大3回**とする。HEAD変更でレビューが無効になり、新規依頼し直す場合も1回として数える。実装チャットと初回のReviewerチャットの2つでやり取りし、別Reviewerへの変更を拒否する。4回目の再レビュー要求は `AUTOMATION_BLOCKED` で拒否する。上限時は未解決の根拠と履歴を元チャットでユーザーへ返し、台帳削除や別PRへの付け替えで自律的に再開しない。仕様変更の承認待ちは修正を進める許可にならない。

通常の `npm run review:lgtm` は台帳の最新レビュー、対象PR・SHA、実装者と異なるReviewer、分類付きLGTM結果、返却記録、実行チャットIDの一致を必須とする。人間のmergeコマンドも独立レビュー情報のない旧形式の通常証跡を拒否する。承認済みアラートハーネスの `--attestation` は既存形式を維持するが、通常の台帳があるPRを迂回する用途には使えない。

台帳はローカルの誤操作防止であり、リモートのチャット実行やツール送信を暗号学的に証明するものではない。チャット作成・待機・送信自体は既存アプリツールで実行し、実際に確認した応答だけを記録する。台帳更新はロックとatomic renameを使う。中断後にロックが残った場合は実行中の処理がないことを確認してから復旧し、履歴を失わない。チャット作成後に登録が失敗した場合は、そのチャットにレビューを開始させず、失敗原因を解消してから同じ作成済みIDを登録する。

## 成功済み検証の再利用

必須テスト・lint・format・buildの実行責任はImplementer / Fixerにある。Reviewerはレビュー対象のコードを変更しないため、対象SHAに対して成功したコマンドとその配下の検証を再実行しない。レビューの独立性は、ユーザー要求・仕様・差分・関連コード・テスト内容の独立した確認で確保する。検証ログやCIの読み取りはコマンドの再実行とは区別する。

成功コマンドの一覧・対象SHA・結果参照が不足する場合やHEADが変わった場合は、Implementerへ不足を返す。Reviewerが必須検証を代わりに回して引き継ぎの欠落を補わない。既存の古い台帳履歴は保持するが、新しいレビュー依頼と最新の通常LGTMには構造化した成功コマンドを必須とする。

追加検証は、成功済みの検証で扱っていない具体的な再現条件・境界値などをコードから特定した場合に限る。実行前にその理由と対象を示し、必要な範囲へ絞る。「念のため」「Reviewerだから」を理由に成功済みの全体検証や同じ個別テストを回さない。実行した追加検証は結果JSONの `additionalChecks` に理由・結果とともに記録し、失敗が残る場合はLGTMを出さない。台帳は引き継ぎ済みコマンドと重複する追加検証の登録を拒否する。

`review:flow status/result/delivered`、`review:lgtm`、チャットの作成・待機・返却、Git/PR/CIの読み取り、外部Task-List同期などのレビュー運営に必要な操作は、この検証再実行禁止とは別である。

## バグ修正と仕様変更の境界

- approved spec、要件、契約、既存の受入条件などから期待動作を特定でき、その動作を壊すバグ・不具合は、元チャットで自律的に修正してよい。修正前の回帰テストの失敗、修正後の成功、必要な全体検証を確認する。
- 「こちらの仕様の方がよい」という設計上の好みや改善提案、要件・API契約・互換性・受入条件を変える指摘は、既存仕様違反の指摘と分けて記載する。提案自体は認めるが、ユーザーの明示承認前にspec・テストの期待値・実装動作を変えない。
- 期待動作が確定できない、文書と実装が矛盾する、バグ修正に見えても仕様変更を含む場合は、元チャットで現状・選択肢・影響を具体的に示してユーザーへ確認し、依存する変更は回答まで進めない。独立した承認済み範囲の作業は継続してよい。
- 仕様変更提案だけで既存契約に違反しない実装をblockerにしない。実害のある既存仕様違反が別にあれば、その根拠を示してblockerとして扱う。レビューを通すために元の仕様や回帰テストを弱めない。

## Reviewerの入力

Reviewer は少なくとも次を独立に確認する。

1. ユーザー要求と対応する `specs/tasks/*.yaml`
2. PRの最新HEAD SHA
3. PR差分と関連コード
4. 変更を直接検証するテスト
5. CIおよびローカル検証結果
6. 既存仕様、アーキテクチャ、セキュリティ制約との整合性

## LGTM

問題がなければReviewerは、現在のPR HEAD SHAに対してLGTMを記録する。

レビュー証跡はGit管理対象外の `.git/foodfolio/review-proof.json` に保存する。`npm run review:lgtm` を使用し、手作業でSHAを書き込まない。

アラート修正ハーネスのReviewerは読み取り専用のまま結果を返す。制御プログラムは元仕様、実装者と異なるReviewerセッションID、成功したレビューのSHA、最新PR HEAD、検証結果を確認してから、`npm run review:lgtm -- --attestation <path>` で証跡を保存する。これは承認済みの責務分離の例外であり、Implementer自身がレビュー結果を作成する許可ではない。ハーネス自身の変更はこの例外による自動承認の対象外とし、Implementerが上記の新規別チャットへ独立レビューを依頼する。

LGTMは記録時点のHEAD SHAだけに有効である。新しいコミットが1つでも追加された場合、以前のLGTMは無効とし、再レビューする。

LGTM記録後、作業終了前に [LGTM時の外部タスクリスト同期](development.md#lgtm時の外部タスクリスト同期) を行う。対応するFoodfolio未完了タスクを根拠付きで完了へ更新し、外部Task-Listで検証・直接コミットする。未完了の作業やユーザー確認が残る項目を一括完了にしない。レビュー対象のFoodfolioファイルには変更を加えず、同期結果と未解決事項を報告する。

## AUTOMATION_BLOCKED

次のいずれかに該当する場合、Reviewerまたは作業エージェントはLGTMを出さず `AUTOMATION_BLOCKED` として停止し、理由と確認済み範囲を報告する。

- 必須CIまたは検証が失敗しており、自動修正対象として解消できない
- Specification as Code の検証に失敗する
- Reviewer blocker が残る
- 変更を直接検証できない、または必要なテストを実行できない
- 仕様と実装が矛盾する
- migration の安全性を確認できない
- security blocker が残る
- 必要な外部APIや外部サービス仕様を確認できない
- 想定外にスコープが拡大し、元仕様のまま安全に進められない
- 自動修正が既定上限に到達する

Reviewerはblockerを返してコードを変更せず停止する。元チャットは上記の分類に従い、既存仕様のまま直せるバグならFixerとして自律的に修正し、検証後に同じReviewerチャットへ再レビューを依頼できる。仕様変更やユーザー判断が必要な停止条件は、明示承認または必要な根拠が得られるまで依存する変更を行わない。

## 人間による最終マージ

ReviewerのLGTM後、AIは作業を終了する。人間は固定コマンド `npm run pr:merge` を実行する。

このコマンドは、現在のPR、ローカルHEAD、レビュー証跡のPR番号と `reviewed_sha` の一致を確認し、`gh pr checks --watch --fail-fast` が成功した後、`gh pr merge --merge --delete-branch --match-head-commit <reviewed_sha>` を実行する。SHAは証跡から自動取得するため、人間が入力しない。

マージ成功後のみレビュー証跡を削除する。検証またはマージが失敗した場合は証跡を残し、原因を確認できるようにする。
