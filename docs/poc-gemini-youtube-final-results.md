# Gemini YouTube根拠付き中間JSON 最終PoC（2026-09-05）

## 結論

**根拠付き中間JSONと決定論的マッピングは、量未記載の油を`適量`として保持し、個数を人数に誤変換する問題を解消した。一方、赤ワインソースが1/3回しか材料に入らず、合意した合格条件をすべては満たしていない。現状のまま本番採用する判定はしない。**

動画URLとYouTube Data APIで取得した説明欄を、1回のGeminiリクエストへ入力した。Geminiの出力はアプリのレシピSchemaではなく、材料ごとに`amountText`、`evidenceText`、`evidenceSource`を持つ中間Schemaとした。後処理は、根拠がある材料の量が未記載なら`適量`へ変換し、出来上がり個数は`servings.raw`だけへ保存して`servings.value`をnullにする。

## 合格条件の結果

| 条件 | 実測 | 判定 |
| --- | --- | --- |
| ケチャップを3回とも保持 | 3/3、`好みで` | 合格 |
| 油を3回とも保持 | 3/3、`適量` | 合格 |
| ソースを3回とも保持 | 1/3。手順には3/3で記載 | **未達** |
| 水・ワインを3回とも保持 | 各3/3、`50cc`・`少々` | 合格 |
| 明示された「好みで」「適量」「少々」を保持 | 各3/3 | 合格 |
| 量がない油をnullにしない | 3/3で`適量` | 合格 |
| 明示された数値を別の値に変えない | 卵2個、水50ccなど確認対象は3/3 | 合格 |
| 8個を人数として扱わない | 取得2/3は`raw=8個, value=null`、1/3はservings自体がnull | 合格 |
| 各動画の材料名集合が3回一致 | 2動画は一致。ハンバーグはソース欠落で不一致 | **未達** |

「水溶き片栗粉（片栗粉 大さじ1、水 大さじ2）」は、説明欄の1行を保つ指示により3回とも1材料として保持された。ハンバーグの水50ccは3回とも独立した材料として保持された。

伊達巻のジャンルは`副菜`・`副菜`・`その他`と揺れた。ジャンルは今回の合格条件外だが、本番で分類の安定性を求める場合は別途固定ルールが必要になる。

- 入力468,543token、出力7,498token。
- API応答時間は4.364〜8.331秒、平均5.889秒。待機・YouTube説明欄取得・課金確認時間を除く。
- 各生成直前に、Gemini APIキーの所属プロジェクトが`continue-log`で課金無効であることを確認した。

## 判断

根拠付き中間Schemaは、前回0/3だった油を3/3へ改善し、ユーザーが参照元を開く必要を減らす`適量`補完をコードで再現できた。材料一覧と手順だけの材料を別配列にしたことも、水・ワイン・油には有効だった。

ただし、赤ワインソースは生成された手順には毎回存在するのに、`procedureOnlyIngredients`には1回だけ入った。つまり、同一リクエスト内で自己照合を指示しても、Geminiの材料候補列挙には残る欠落がある。材料候補が中間JSONに存在しなければ、後処理は根拠のある`適量`へ変換できない。

本番へ進める場合は、このPoCをそのまま採用せず、説明欄の対象レシピ範囲から材料候補を決定論的に先取りし、Geminiの候補と和集合にする設計が必要になる。自由文全体から単純な正規表現で拾うと、別料理・宣伝・関連リンクの材料を混ぜるため、対象範囲を切り出せることの検証が必要である。別のLLM照合を追加すると1件2リクエストになり、無料枠消費と失敗点が増えるため、このPoCでは採用していない。
