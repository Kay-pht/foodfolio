# foodfolio MVP PoC検証計画書

## 1. 本書の目的

本書は、foodfolio MVPの技術選定において、机上確認だけでは不確実性が残る項目に限定してPoCを実施するための検証計画を定義する。

PoCの目的は、すでに公式ドキュメント等で実現可能と確認できる技術を再検証することではない。

MVP成立に直接影響する以下の不確実性だけを、最小限のコードと実データで確認する。

1. 外部URLからAI解析に必要なレシピ情報を取得できるか
2. 取得した情報からAIでfoodfolio用の構造化レシピを十分な精度・コストで生成できるか
3. 実URLから構造化レシピ生成までの一連の処理が成立するか

PoC用コードは本番実装を目的とせず、必要に応じて破棄できる検証コードとして扱う。

---

## 2. PoC対象外

以下は採用技術として実現可能性が公式ドキュメント等で確認できており、今回のPoCでは独立した検証対象にしない。

- Swift / SwiftUIによるiOSアプリ開発
- Firebase AuthenticationによるApple / Google / Email認証
- Firebase ID Tokenを利用したBackend認証
- Cloud RunでのNode.js / TypeScript実行
- Cloud TasksからCloud Runへの非同期HTTP配送
- PrismaからPostgreSQLへの接続
- Neon PostgreSQLの利用
- FCM + APNsによるiOS Push Notification
- TerraformによるGCPリソース管理
- Firebase Crashlytics / Analytics

これらは本実装時に公式手順に沿って構築し、通常の実装テストで確認する。

Cloud RunとNeon間のレイテンシも現時点では独立PoCを設けない。MVP規模で実装中に問題が確認された場合のみ追加検証する。

---

## 3. PoC全体方針

### 3.1 原則

- 完成アプリは作らない
- UIは原則作らない
- 本番用アーキテクチャを先行実装しない
- 検証したい不確実性に必要な最小コードだけを書く
- 同じ入力データを再利用できるようにする
- 検証結果は数値または具体例で記録する
- 「動いた」だけでなく、MVPで使える水準かを判断する

### 3.2 想定配置

PoCコードは以下のような本番コードと明確に分離した場所へ置く。

```text
poc/
├─ url-extraction/
├─ ai-extraction/
└─ end-to-end/
```

実際のディレクトリ構成はPoC着手時に必要最小限で決める。

# 4. PoC 1 — 外部URL情報取得

## 4.1 目的

foodfolioが対象とする外部URLから、AI解析および一覧表示に利用できる情報を取得できるか確認する。

確認したいのは単にHTTPリクエストが成功するかではなく、**レシピ構造化に十分な入力データを取得できるか**である。

## 4.2 対象ソース

最低限、以下を確認する。

- 一般的なレシピWebサイト
- クラシル
- クックパッド
- YouTube
- Instagram
- TikTok

必要に応じて複数URLを使い、1件だけの成功で判断しない。

## 4.3 取得対象

各URLについて、可能な範囲で以下を確認する。

- 本文またはレシピ情報に相当するテキスト
- OGP / サムネイル等の代表画像URL
- 元サービス / ドメインの判定に必要な情報
- AIへ渡す入力として利用可能なテキスト量・内容

料理名は保存直後の仮タイトル用途には使用しないため、ページタイトル取得自体をMVP成立条件には含めない。

## 4.4 確認観点

各サービスについて以下を記録する。

| 観点 | 内容 |
| --- | --- |
| HTTP取得 | 通常のHTTPリクエストで取得できるか |
| 本文情報 | レシピ解析に有用なテキストが取れるか |
| 画像 | 代表画像を取得できるか |
| JS依存 | JavaScript実行が必要か |
| 認証依存 | ログインやCookieが必要か |
| 安定性 | 複数URLで同様に取得できるか |
| 実装複雑度 | 共通処理で扱えるか、サービス別処理が必要か |

## 4.5 PoC結果で決めること

- MVPで正式対応できるソース範囲
- URL取得の基本方式
- サービス別Extractorが必要か
- AI入力へ渡す前の前処理方針
- 画像URL取得方式
- MVPでは対応困難として除外すべきサービスがあるか

## 4.6 完了条件

各対象サービスについて、以下のいずれかを明確に判定できれば完了とする。

- MVPで利用可能
- 条件付きで利用可能
- MVPでは対応しない

「追加調査が必要」のまま主要サービスが残っている場合はPoC未完了とする。

# 5. PoC 2 — AIレシピ構造化

## 5.1 目的

PoC 1で取得できる実データを入力として、AIがfoodfolioのレシピデータを十分な精度で構造化できるか確認し、MVPで利用するAI Provider / Modelを決定する。

一般的なLLMベンチマークではなく、foodfolio固有の抽出タスクで評価する。

## 5.2 比較候補

候補はPoC実施時点の価格・提供状況を再確認したうえで選定する。

現時点では以下を主な比較対象とする。

- Google Gemini
- OpenAI
- Z.ai
- DeepSeek

全Providerの全モデルを比較する必要はない。

各Providerから、構造化抽出用途として価格と性能のバランスが良いモデルを1つ程度選び、比較対象を絞る。

## 5.3 共通出力形式

全モデルへ原則同じ要求を与え、同一Schemaに変換する。

概念例：

```json
{
  "title": "料理名",
  "servings": 2,
  "cookingTime": "20分",
  "genre": "主菜",
  "ingredients": [
    {
      "name": "鶏もも肉",
      "amount": "200g"
    }
  ],
  "steps": [
    "..."
  ]
}
```

実際のSchemaはPoC開始時に基本設計の保存項目と合わせて固定する。

## 5.4 テストデータ

同一の固定テストセットを全モデルへ入力する。

テストセットには以下を混在させる。

- 情報が明確なレシピ
- 材料や分量表記が複雑なレシピ
- 人数記載あり / なし
- 調理時間あり / なし
- 手順あり / 取得困難
- SNS由来の短い説明文
- Webページ由来のノイズを含むテキスト

PoC 1で実際に取得した入力データを優先して使用する。

## 5.5 評価項目

### 精度

- 料理名
- 材料名
- 分量
- 基準人数
- 調理時間
- ジャンル
- 調理手順

### 品質

- 原文に存在しない情報を推測・補完していないか
- 材料と分量の対応が崩れていないか
- 手順の欠落や過剰な要約がないか
- 情報がない項目を適切に空として扱えるか

### 機械処理性

- JSONとして正常に解析できるか
- Schema validationに成功するか
- 同じ入力で大きく結果がぶれないか

### コスト

- 1レシピあたりのおおよそのAPI利用料
- 入力Token
- 出力Token

### 参考値

- 応答時間

AI解析は非同期処理のため、応答時間は主要評価項目にはしない。

## 5.6 選定基準

価格最安だけでは決めない。

以下の優先順位で総合判断する。

1. 原文に忠実な抽出精度
2. hallucinationの少なさ
3. Schema成功率
4. 1レシピあたりコスト
5. 応答時間

多少高くても明確に精度が高い場合は採用候補とする。

逆に非常に安価でも、材料・分量・人数等に実用上問題があるモデルは採用しない。

## 5.7 PoC結果で決めること

- MVPの標準AI Provider
- MVPの標準Model
- 利用するStructured Output方式
- 必要なPrompt / System Instructionの基本方針
- Validation失敗時の基本的な扱い
- AI Provider切替を可能にするAdapter方針の妥当性

## 5.8 完了条件

少なくとも1つのモデルについて、以下を満たすと判断できればAI PoCを完了とする。

- foodfolioで必要な情報を実用可能な精度で抽出できる
- hallucinationが許容できる水準である
- 構造化出力を安定してアプリ側Schemaへ変換できる
- MVP利用量でコストが許容可能である

選定したモデルと、他候補を不採用にした理由を記録する。

# 6. PoC 3 — URL取得からAI解析までの統合確認

## 6.1 目的

PoC 1とPoC 2を個別に成功させた後、実URLを起点に一連の処理が成立することを確認する。

```text
実URL
↓
URL情報取得
↓
AI入力用テキスト生成
↓
AI解析
↓
Schema validation
↓
構造化レシピJSON
```

Cloud Run、Cloud Tasks、Neon等を含む本番インフラ全体を作る必要はない。

このPoCで確認するのは、**実際に取得できるデータ品質と採用AIの組み合わせでレシピ構造化が成立するか**である。

## 6.2 対象

PoC 1でMVP対応可能と判断した主要ソースから数件ずつ選ぶ。

特に入力形式が異なるサービスを優先する。

## 6.3 確認観点

- URL取得結果をそのままAI入力へ利用できるか
- 不要なHTML / ナビゲーション / 広告等がAI精度を悪化させないか
- 前処理が必要か
- AI出力がfoodfolio Schemaに変換できるか
- 情報未取得と解析失敗を区別できる材料が得られるか

## 6.4 PoC結果で決めること

- URL取得からAI入力までの前処理方針
- 本番Workerへ実装する大まかな解析パイプライン
- MVP対応ソースの最終確認
- 実装設計へ進んでよいか

## 6.5 完了条件

MVP対応対象とした主要ソースについて、実URLから構造化レシピJSONまで一連の処理が成功すること。

一部項目を取得できないケースは失敗とはしない。

以下のように判定できればよい。

- 取得できる情報は正しく構造化される
- 原典にない情報を勝手に補完しない
- 取得できない任意項目は空として扱える
- 処理自体の異常は解析失敗として区別できる

# 8. PoC完了時に確定する事項

PoC完了後、最低限以下を確定する。

- MVP対応URLソース
- URLコンテンツ取得方式
- サービス別Extractorの要否
- AI入力前処理方式
- AI Provider
- AI Model
- AI出力Schema / validation方針
- URL取得 → AI解析の処理パイプライン

確定した内容は `docs/technology-selection.md` へ反映する。

必要に応じて要件定義・基本設計で定義したMVP対応範囲にも反映する。

# 9. 技術選定・技術検証の完了条件

以下をすべて満たした時点で `todo.md` の「技術選定・技術検証」を完了とする。

- PoC 1を完了し、MVP対応ソースと取得方式が決まっている
