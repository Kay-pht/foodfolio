# レシピ管理アプリ MVP 開発フロー

## 開発方針

本MVPでは、設計書を大量に作ることよりも、

**「実装前に重要な判断だけ済ませ、早く動くものを作り、実ユーザーで検証する」**

ことを優先する。

前提：

* 開発者：1人
* 対象：iOS
* MVPゴール：TestFlightで外部ユーザーに配布
* UI/UX：ワイヤーフレーム中心
* 課金：MVP対象外
* 開発ドキュメント：実装・判断に必要なものだけ作成

---

# 全体フロー

```text
① 要件定義
    ↓
② 基本設計・UI/UX設計
    ↓
③ 技術選定・技術検証
    ↓
④ 実装設計
    ↓
⑤ 実装 + テスト
    ↓
⑥ TestFlightリリース準備
    ↓
⑦ MVPリリース + ユーザー検証
```

---

# ① 要件定義

## 目的

**「何を作るか」と「何を作らないか」を固定する。**

途中で機能が増え続けることを防ぐ。

## 決めること

* プロダクトの目的
* ターゲットユーザー
* 解決する課題
* MVP機能
* MVP対象外機能
* 主要ユーザーフロー
* 保存する情報
* 検索対象
* MVP完了条件

## 成果物

* `docs/requirements-specification.md`

## 完了条件

「MVPにこの機能を入れるべきか？」と聞かれたときに、要件定義書を見れば判断できる状態。

# ② 基本設計・UI/UX設計

## 目的

実装前に、

**「ユーザーがどう操作するか」と「アプリがどう構成されるか」**

を決める。

詳細なビジュアルデザイン制作は行わない。

## MVP主要画面

* 認証
* レシピ一覧
* URL追加Sheet
* レシピ詳細
* レシピ編集
* 検索
* 設定
* アカウント

タグ管理は独立画面にしない。

タグの新規作成・付与・解除はレシピ詳細 / 編集画面から行う。

## 主要UI方針

* レシピ一覧をホームとする
* Bottom Tabは使用しない
* 左上foodfolioアイコンからPush型Drawerを開く
* Drawerは設定 / アカウントのみ
* レシピ一覧は2列グリッド
* URL追加は右下FABからSheet表示
* 検索のジャンル / タグはDropdown
* 検索ワードなしでもジャンル / タグのみで絞り込み可能
* タグ追加は別画面ではなくBottom Sheet
* タグ管理画面はMVP対象外

## 主要ユーザーフロー

```text
ログイン
↓
レシピ一覧
↓
URL追加Sheet
↓
URL貼り付け
↓
即保存
↓
解析中
↓
AI解析完了 / 失敗
↓
検索・閲覧可能
```

## UI

FigJamでLow-fiワイヤーフレームを作成する。

ここでは、

* ボタン位置
* 画面遷移
* 情報配置
* Dropdown / Sheetなどの操作形式
* loading / empty / error状態

が分かれば十分。

ビジュアルデザインの完成度は求めない。

## 成果物

* `docs/basic-design.md`
* `docs/ui-ux-design.md`
* FigJamワイヤーフレーム
  * https://www.figma.com/board/jL7FstV1ZltOhmeaIEHkOo

## 完了条件

画面を見ながら、

**「ユーザーが保存・タグ付け・検索・設定操作をどう行うか」**

を一通り説明できる状態。

# ③ 技術選定・技術検証

## 目的

実装を始めてから発覚すると致命的な技術リスクを先に潰す。

MVPでは特に重要な工程。

## 技術選定

最低限以下を決定する。

### iOS

* Swift / SwiftUI等

### Backend

* Backend技術
* API構成
* ホスティング

### Database

最低限以下を扱える構成とする。

* ユーザー
* レシピ
* 材料
* タグ
* レシピとタグの関連
* AI解析状態
* 必要に応じて検索履歴
* 通知設定

### Authentication

UI上の対応方式は以下で確定済み。

* Apple
* Google
* メール

メールではログイン、新規登録、パスワードリセットを扱う。

この工程では、それらを実現する認証基盤・SDKを決定する。

### Notification

* 解析成功 / 失敗通知の実現方式
* iOS通知権限の扱い
* Backendからの通知が必要か

設定UIは「レシピ解析通知」1トグルで、ONなら成功・失敗の両方、OFFなら両方通知しない。

### AI

* 利用するAI API
* 入出力形式

### 非同期処理

```text
URL保存
↓
バックグラウンド解析
↓
DB更新
↓
アプリへ反映
↓
通知設定ONなら成功 / 失敗を通知
```

を実現する方法。

---

## 技術検証（Spike / PoC）

アプリ全体を試作する必要はない。

**失敗するとMVP成立そのものに影響する部分だけ検証する。**

### PoC 1

URLから以下を取得できるか。

* title相当情報
* thumbnail
* 本文情報

ただし、本番の保存経路ではWebページタイトルを仮タイトルに利用しない。

### PoC 2

取得した情報からAIで以下を抽出できるか。

* 料理名
* 材料
* 分量
* 人数
* 調理時間
* ジャンル
* 調理手順

### PoC 3

主要サイトで成立するか。

最低限：

* YouTube
* Instagram
* TikTok
* クラシル
* クックパッド
* 一般Webサイト

### PoC 4

バックグラウンド解析フローが成立するか。

```text
URL保存
↓
即レスポンス
↓
非同期解析
↓
解析結果保存
```

## 成果物

* 技術スタック一覧
* 簡単な構成図
* PoCコード
* 技術検証結果

## 完了条件

MVPのコアである

**「URL → 保存 → 自動解析 → 検索」**

を技術的に実現できる見通しが立っていること。

# ④ 実装設計

従来の「詳細設計」に相当する工程。

ただし、個人MVPなので詳細設計書を大量には作らない。

## 目的

実装中に構造を考え続けなくて済む程度まで整理する。

## 決めること

### データモデル

例：

```text
User

Recipe
- id
- userId
- url
- source
- title
- imageUrl
- genre
- analysisStatus
- createdAt

Ingredient

Tag

RecipeTag

UserSetting
```

タグ管理画面は存在しないが、タグ自体の保存とレシピとの関連付けは必要。

### API

例：

```text
POST /recipes
GET /recipes
GET /recipes/:id
PUT /recipes/:id
DELETE /recipes/:id

GET /recipes/search
```

必要に応じてタグ、設定、認証関連APIを追加する。

### 検索

以下を具体化する。

* 料理名 / 材料のテキスト検索
* ジャンル絞り込み
* タグ絞り込み
* ワードなしフィルタリング
* 条件組み合わせ
* タグDropdownの単一 / 複数選択仕様
* 検索ワード履歴の保存場所と更新タイミング

### AI解析フロー

```text
URL
↓
Web情報取得
↓
AI解析
↓
JSON化
↓
DB保存
```

### 状態管理

最低限、

```text
pending
processing
completed
failed
```

などの解析状態を決める。

### 通知

* completed / failedの通知条件
* 通知設定OFF時の抑止
* 通知権限未許可時のUI

### エラー処理

* URL取得失敗
* AI解析失敗
* サムネイル取得失敗
* unsupported page
* 通信失敗
* 認証失敗
* 通知失敗

など。

## 成果物

* データモデル
* API一覧
* AI解析仕様
* 状態遷移
* 検索仕様
* 通知仕様
* 必要最低限のエラー仕様

## 完了条件

実装時にデータ構造やAPIについて大きく迷わない状態。

# ⑤ 実装 + テスト

## 方針

すべて実装して最後にテストするのではなく、

**機能単位で実装 → 動作確認**

を繰り返す。

## 推奨実装順

### 1. アプリ基盤

* iOSプロジェクト
* Backend
* DB
* Apple / Google / メール認証
* 開発環境

### 2. レシピ保存

```text
URL入力
↓
DB保存
↓
一覧表示
```

まずAIなしで成立させる。

### 3. メタ情報取得

* thumbnail
* source
* AI解析入力に必要な本文情報

### 4. AI解析

* 料理名
* 材料
* 分量
* 人数
* 調理時間
* ジャンル
* 調理手順

### 5. 非同期処理

* 解析中表示
* completed反映
* failed処理

### 6. レシピ詳細・編集

* 人数変更表示
* 編集可能項目
* 元レシピ導線
* 削除

### 7. タグ

MVPでは以下のみ実装する。

* 新規作成
* レシピへの付与
* レシピから解除

タグ名変更・タグ削除・独立タグ管理画面は実装しない。

### 8. 検索

* 料理名
* 材料
* ジャンル
* タグ
* ワードなしフィルタリング
* 検索ワード履歴

### 9. 設定・通知・アカウント

* レシピ解析通知1トグル
* 成功 / 失敗通知
* ログイン情報
* ログアウト
* アカウント削除

### 10. UI調整

最後に最低限整える。

# テスト方針

MVPでは網羅的なテストは目指さない。

ただし、重要ロジックには自動テストを書く。

## 自動テスト優先対象

* URL登録
* AI解析結果の変換
* データ保存
* 人数変更時の分量計算
* 検索・フィルタリング
* タグ付与 / 解除
* ユーザーごとのデータ分離
* 通知条件

## 手動テスト

主要ユーザーフローを実機で確認する。

```text
ログイン
↓
URL保存
↓
解析
↓
タグ追加
↓
検索 / ジャンル・タグ絞り込み
↓
レシピ詳細
↓
元サイトを開く
```

加えて以下を確認する。

* 検索ワードなしでジャンル / タグ絞り込みできる
* タグ追加で別画面に遷移せずBottom Sheetが出る
* 検索フィルターがDropdownで開く
* 解析通知ONなら成功 / 失敗の両方が通知対象になる
* 解析通知OFFなら両方通知しない
* ログアウトとアカウント削除がアカウント画面に存在する

# ⑦ MVPリリース + ユーザー検証

## MVPゴール

TestFlightで外部ユーザーに配布する。

MVPは、**「完成品を公開する」**ことではなく、**「このプロダクトに価値があるかを確認する」**ことが目的。

## MVPで検証すること

### 保存

* 本当にレシピを保存するか
* 何件保存するか
* URL貼り付けが面倒ではないか

### AI解析

* 料理名は適切か
* 材料抽出は使える品質か
* ジャンル分類は適切か
* 手順抽出は実用的か

### 検索

* 実際に検索を使うか
* 材料検索を使うか
* タグ検索を使うか
* ジャンル・タグのみの絞り込みを使うか

### タグ

* レシピ単位のタグ付与を使うか
* タグ管理画面がなくてもMVP利用上問題がないか

### 継続利用

最も重要。

```text
レシピ発見
↓
このアプリに保存
↓
後日また使う
```

という行動を繰り返すかを見る。

```text
継続

改善

次機能
```

* iOS Share Extension

# 開発フローの判断基準

各工程で完璧を目指さない。

以下だけ満たしたら次へ進む。

| 工程 | 次へ進む条件 |
| --- | --- |
| 要件定義 | 作るもの・作らないものが明確 |
| 基本設計・UI/UX | 主要画面と操作が明確 |
| 技術検証 | コア機能が技術的に実現可能 |
| 実装設計 | DB / API / 処理フローが決まった |
| 実装 | 主要ユーザーフローが動作 |
| リリース準備 | 第三者が利用できる |
| MVP検証 | 実ユーザーの利用データを取得 |

# 最重要原則

このMVPでは、

```text
必要最低限の設計
↓
技術リスクを先に検証
↓
コア体験を実装
↓
外部ユーザーへ配布
↓
利用実態から判断
```

という流れを採用する。

特に個人開発では、③の技術検証を省略して本実装へ進まないことを重要ルールとする。
